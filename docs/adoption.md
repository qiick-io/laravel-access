# Adoption

Product adoption order (design §10): package `0.1.0` → **excubia-app** →
signaculum-core → instituta-core → **externa-core** last → then
`qiick/laravel-api-keys` in each product.

Each product:

1. Binds `ActorContext` after credential verification (`AccessContext::enter`).
2. Binds `PermissionVocabulary`, `RoleCatalog`, `GroupRoleSource` (default
   Eloquent), `TeamContext` (`NoTeamContext` today), the 2FA policy and
   responder, and the authorization responder.
3. Sets `permission.register_permission_check_method` to `false` and
   `permission.events_enabled` to `true`.
4. Replaces its resolver copy, 2FA middleware, permission middleware and
   FormRequest trait, and `Gate::before` closure with this package (see
   "Permission middleware and FormRequest trait" below).
5. Rewrites Policy `$actor->can(PermissionEnum…)` calls to the resolver (R5).
6. Lists remaining direct `hasPermission()` call sites in `qiick-standards.json`
   (`access.direct_checks`) with reason, decision link and `review_by`.

Jobs dispatched while an API actor is bound receive that actor automatically
(queue payload stamp via `ActorPayloadStamper`). Prefer
`Illuminate\Contracts\Queue\ShouldBeEncrypted` on those jobs when the queue
store is not encrypted end-to-end. `CarriesActorContext` via `through()` remains
available for explicit opt-in. The package never calls
`Queue::createPayloadUsing(null)`, so other payload hooks (including Laravel's
`illuminate:log:context`) keep working.

Organisation-scoped work must call `TeamContext::switchTo(...)` itself inside
the job (or middleware). Async workers start with a cleared Spatie team id so
job 2 never inherits job 1; a sync-connection job nested under a request
restores the request team afterwards and does not wipe it mid-request.

Under PHPUnit, `runningInConsole()` is always true, so the API-guard signal is
ignored by default. Product tests that need the guard path should call
`Qiick\Access\Testing\TrustApiGuardInConsole::enable()` (sets
`access.trust_api_guard_in_console`) and `disable()` in tearDown. The resolver
honours that flag only when `app()->environment('testing')` is true.

The package ships migrations for fixed table names `user_groups`,
`user_group_user` and `user_group_role` (with `public_id`, `metadata`,
membership `expires_at`, nullable `organisation_id`, and `is_instance`).
Names are not configurable (Q5). Spatie's tables stay Spatie's.
`access.migrations.groups` defaults to `true`; externa 1.x sets it to `false`
and adopts the same shape through an additive migration so its released
tables keep the standard names until v2 (new columns stay nullable / unused
there). Pre-1.0 products delete their own `create_user_groups_tables`
migration.

The package also ships the `principals` table (design §15), loaded while
`access.migrations.principals` is `true` (the default):

- `id` (UUID v7, generated by the model), `type`, `user_id` (**restrict on
  delete**: a user with principals cannot be deleted until erasure unlinks
  them), `organisation_id` (no foreign key: the product adds one to its
  organisations table in its own migration, **restrict on delete**, never
  cascade or set null), `owner_principal_id` (null on delete), `name`,
  `created_by` (null on delete), `expires_at`, `deactivated_at`,
  `deactivation_reason`, `metadata`;
- UNIQUE (`organisation_key`, `user_id`), where `organisation_key` is a stored
  generated column (the organisation id, or `''` at instance level): one
  principal per user and organisation, and one per user at instance level,
  with no NULL hole on any engine;
- products with organisations set `access.principals.organisation_required`
  to `true` **before migrating**: a CHECK (triggers on SQLite) then requires an
  organisation on every principal except the `access.principals.instance_types`
  (lower-case type names, each with a decision note; only allowed together
  with `organisation_required`), which must have neither organisation nor user
  and are singletons per type. The config is read when the migration runs:
  changing it later changes nothing in the database.

SQLite rebuilds a table when a migration alters it (adding the organisation
foreign key, for example) and drops its triggers, which carry the
organisation and instance-group rules there. The provider calls
`Qiick\Access\Laravel\AccessSchema::ensureConstraints()` after every
`migrate` run (`MigrationsEnded`, skipped for `--pretend`), which recreates
them and is a no-op where the rules already exist. A product migration that
alters `principals` or `user_groups` should still call it at its end: when a
later migration of the same batch fails, `MigrationsEnded` never fires. The
rules apply only to tables the package owns (`access.migrations.groups` /
`access.migrations.principals`), and only on the migrated connection.
Connections with a table prefix are not supported.

Pre-1.0 products delete their own `create_principals_table` (or the
`principals` block of a larger migration) and recreate the database.

Products create and deactivate principals through
`Qiick\Access\Principals\PrincipalDirectory` (bound by the provider), never
by writing rows directly; the `Principal` model is fully guarded.

- `forMember($user, $organisationId)`: the user's principal in an
  organisation (`null`: instance level). Idempotent. A principal deactivated
  as `offboarded` is reactivated; one deactivated for any other reason
  (`admin`, `owner_deactivated`, `expired`) is returned as it is, inactive, so
  an administrator's decision outlives the next login; an `erased` one throws.
  Organisation ids are stored in lower case;
- `createService($type, $organisationId, $name, $owner, $createdBy,
  $metadata)`: a service or agent account. The type must be listed in
  `access.principals.types`; `user` and the instance types have their own
  methods; the owner must be active, in the same organisation, and its chain
  at most eight principals long and acyclic;
- `instance($type, $name)`: the singleton of a declared instance type (only
  with `organisation_required`). It is returned even when deactivated: check
  `isActive()` before use;
- `deactivate($principal, DeactivationReason)`: deactivates the principal,
  unless it already is (an erased tombstone is never rewritten), and every
  active principal it owns, in one transaction. `PrincipalDeactivated` (with
  the owned ids) is dispatched after the surrounding transaction commits.
  **Revoke their API keys in a listener** (qiick/laravel-api-keys reason
  `owner`);
- `eraseUser($user, fn ($user) => $user->forceDelete())`: GDPR erasure in
  one transaction. Every principal of the user becomes an `erased` tombstone
  (user unlinked, name anonymised), the principals it owns are deactivated,
  then the closure hard-deletes the user. If the user row still exists
  afterwards (a soft delete, or no delete), `eraseUser()` throws and rolls
  everything back: an erasure that keeps the person's data, or lets a restore
  mint a fresh principal past the tombstone, never commits.
  `principals.user_id` is `ON DELETE RESTRICT`, so deleting a user who still
  has principals any other way throws `UserHasPrincipalsException` (a soft
  delete is allowed, since it keeps the row). The users model and the
  principal model must use one database connection: `eraseUser()` refuses
  otherwise, because the user delete would wait on its own locks;
- `isActive($principalId)`: the use-time check behind a key: not deactivated,
  not expired, a `user` principal still has its user, an instance-level row
  is one the organisation rule allows, and every owner up the chain is active.
  Never cached; it reads one row per owner, so at most eight queries.

The directory reads `access.principals.organisation_required` and
`instance_types` at runtime while the database rule was fixed when the
migration ran: keep them unchanged after migrating, or the database refuses
what the directory allows with a driver error.

`access.principals.model` may point at a subclass of
`Qiick\Access\Principals\Principal` for product relations (API keys,
grants).

Prove the schema on the freshly migrated database (design §15.6, P9) with
`Qiick\Access\Testing\AssertsPrincipalsSchema`:

```php
$probe = new AssertsPrincipalsSchema(
    DB::connection(),
    fn (): int => User::factory()->create()->id,
    // Products with an organisations table and its foreign key:
    fn (): string => Organisation::factory()->create()->id,
    fn (string $organisationId) => DB::table('organisations')->where('id', $organisationId)->delete(),
);
$probe->assertShape();
$probe->assertConstraints();
```

`assertConstraints()` tries, inside rolled-back transactions, a second
principal for one membership (and one instance-level user when organisations
are optional), deleting a user who still has a principal, deleting an
organisation that still has principals (when the delete closure is given), an
organisation-less principal when organisations are required, and for each
declared instance type a principal with a user and a second principal. It
fails if the database accepts any of them; only integrity refusals count, so
any other database error propagates. Run it on every engine the product
supports, SQLite included.

Products generate `user_groups.public_id` as **UUID v7** in their Eloquent
model / factory (the package migration only declares the column). The
membership FK targets `access.users_table` when set, otherwise the table from
`auth.providers.users.model`, otherwise `users`. The instance super-admin
group uses `is_instance = true` with `organisation_id` NULL; a CHECK forbids
`is_instance = true` together with a non-null `organisation_id`.

A group name is unique within its organisation, and among the groups without
an organisation (instance groups and the legacy unscoped ones): two
organisations can both have an "Editors" group. The migration indexes
(`organisation_key`, `name`), where `organisation_key` is a stored generated
column holding the organisation id, or `''` without one, so organisation-less
duplicates are refused on every engine (a plain NULL would let them through).
externa 1.x keeps its own tables with a global unique `name`, which
`AssertsGroupTablesSchema` accepts because it has no organisations; it adds
`organisation_key` with the unique index when it moves to the package tables
(additive).

Assert the group schema with `Qiick\Access\Testing\AssertsGroupTablesSchema`
(AC17 / C75). When Spatie teams are on, set
`permission.column_names.team_foreign_key` to `organisation_id` and use uuid
team columns; products assert that with
`Qiick\Access\Testing\AssertsSpatieTeamSchema` (A3) — run the uuid check on
PostgreSQL.

`EffectivePermissionResolver` applies group role ids from instance groups,
legacy unscoped groups, and organisation groups matching the current
`TeamContext`. Super-admin via groups counts **only** `is_instance` groups
(C30). Under teams, only the **global** super-admin role (no
`organisation_id` on the role) counts, whatever team the assignment was made
in; a team-local role with the reserved name never mints an instance
super-admin, and the package refuses to save one. Group memberships count
only for models on the table and connection of `access.group_member_model`
(default `auth.providers.users.model`), so another guard's principal with the
same id, a subclass with its own table included, inherits no group roles. With
teams, bind `TeamContext` to `SpatieTeamContext` through the container
(`singleton(TeamContext::class, SpatieTeamContext::class)`): that binding wires
the resolver flush its constructor requires. `isDirectSuperAdmin()` is the same filter-off check for a **direct**
role only — products use it with `TwoFactorPolicy::hasUsableFactor()` for
break-glass (P6); the OIDC break-glass seam stays outside this package (R7).
Register `EnsureTwoFactorIsEnabled` on the web stack; exempt routes live in
`access.two_factor.exempt_route_names`. Bind `ActiveUsers` and use
`SuperAdminGuard` for super-admin grant/revoke and last-admin protection.
Demotion (or soft-delete / expiry) paths that bypass
`SuperAdminGuard::wouldLeaveNoActiveSuperAdmin` stay a product adoption
checklist item — the package cannot see those call sites.
Products must set `permission.register_permission_check_method` to `false` and
`permission.events_enabled` to `true` before boot; the provider fails closed
otherwise (R4, A1). Bind `RoleCatalog`, `TwoFactorPolicy`,
`TwoFactorResponder` and `AuthorizationResponder` or boot fails (AC12).

## Permission middleware and FormRequest trait

The package does not register a middleware alias (it would collide with the
product's own). Register it in `bootstrap/app.php`:

```php
->withMiddleware(function (Middleware $middleware): void {
    $middleware->alias([
        'permission' => \Qiick\Access\Http\EnsureUserHasPermission::class,
    ]);
})
```

and gate route groups with `permission:<PermissionEnum value>`.
`permission:a,b` requires **all** listed permissions; a route with none
throws. Spatie's `a|b` and wildcard syntaxes are not supported: names match
exactly, so they deny. In a FormRequest, `use AuthorizesWithPermission;` and
call `$this->authorizePermission(PermissionEnum::X->value)` from
`authorize()`. Denials use the product `AuthorizationResponder` body in both.

A web actor passes with the permission from the resolver, super-admin
included, only when the request's guard is in `access.web_guards` (default
`web`) and its user is the bound `AccessContext` user, if one is bound. An API
actor passes only when the credential's scopes allow the permission **and** its
owner currently holds it (read fresh, never through super-admin: neither the
vocabulary grant nor permissions attached to the super-admin role count). The
scope half is the product's (or `qiick/laravel-api-keys`'s)
`ApiActorScopeCheck` binding; with none bound, every API actor is denied.

**Classify every guard.** Boot fails unless each guard in `auth.guards` is in
`access.web_guards` or `access.api_guards` (`ACCESS_API_GUARDS`, Sanctum's
`sanctum` guard included). A token guard in neither would make its users look
like web sessions. Two consequences:

- With `ACCESS_API_GUARDS=sanctum`, every request through `auth:sanctum` is an
  API actor, including a first-party SPA's cookie-authenticated requests.
  Put first-party SPA routes behind `auth:web` so they stay web sessions.
- A product's own session guard (a Filament panel guard, for example) goes in
  `ACCESS_WEB_GUARDS` (comma-separated; default `web`).

At runtime the rule holds for guards added after boot too:
on HTTP, any default guard outside `access.web_guards` resolves as an API
actor, so it never gets the super-admin pass.

## Conformance helpers (tests only)

`Qiick\Access\Testing\ProbeAbility::register($this->app)` defines the AC2
probe ability (always `false`) and returns its name. A super-admin web session
passes it; the same user behind a key, an OAuth grant or the public door must
not. Call `ProbeAbility::enable()` in the test suite first: registering throws
outside a unit-test run and without that explicit opt-in, so `APP_ENV=testing`
alone never activates it.

`Qiick\Access\Testing\DirectPermissionCheckScanner` is the AC9 static check:

```php
$violations = (new DirectPermissionCheckScanner(PermissionEnum::class))
    ->scan(base_path(), ['app', 'routes'], base_path('qiick-standards.json'));

expect($violations)->toBe([]);
```

It fails on any Gate ability call (`can`, `cannot`, `cant`, `canAny`,
`allows`, `denies`, `authorize`, `inspect`) with a permission inside a Policy,
on one whose ability it cannot read statically, and on dynamically named calls
in Policies, and on any static `Gate::` method outside the known Gate API (a
macro). Class attributes count as part of their class, and trait aliases of a
watched method (`use T { hasPermission as checkPermission; }`) count as that
method. Outside Policies and the Inertia share (`share()` of
`App\Http\Middleware\HandleInertiaRequests`, or the class passed as the
scanner's third argument), each direct `hasPermission()` /
`hasAssignedPermission()` site must be listed:

```json
"access": {
  "direct_checks": [
    { "site": "App\\Ai\\Agents\\AppAssistant::tools", "reason": "tool inventory before a model exists",
      "decision": "knowledge/...", "review_by": "2027-03-01" }
  ]
}
```

A site is `Class::method` (closures and anonymous classes count as their
enclosing method), or the file path for code outside classes. Entries need a
reason, a decision and a `review_by` date that has not passed, and an entry
whose site has no check left fails, so the list only shrinks.

Known limits: a method name built at runtime from pieces (`'has'.'Permission'`)
or read from configuration (`$resolver->{config('...')}(...)`) is not seen
outside Policies; inside a Policy any dynamically named call fails. A watched
name counts as a callable string only when assigned to a variable, used as a
braced method name or passed after an object (`[$object, 'name']`), so data
strings such as `return 'can';` are not flagged.

`SuperAdminGuard` last-admin protection relies on `SELECT … FOR UPDATE`.
SQLite does not honour those locks; production deployments must use MySQL,
MariaDB or PostgreSQL.

## Legacy `Gate::before` and shadow mode (externa only)

`externa-core` switches to the package `Gate::before` behind a flag, after a
shadow comparison (design §9.2 step 6 and §9.4). Other products leave both
switches at their defaults. Both are removed in v2.

- Bind `Qiick\Access\Contracts\LegacyGateBefore` to the product's old
  `Gate::before` logic.
- `access.use_package_gate` (`ACCESS_USE_PACKAGE_GATE`, default `true`)
  chooses which callback decides. The package still registers exactly one
  `Gate::before` (AC1).
- `access.gate_shadow` (`ACCESS_GATE_SHADOW`, default `false`) also runs the
  other callback and logs each disagreement as `access.gate_shadow_mismatch`
  on `access.gate_shadow_log_channel` (default channel when null). The log
  holds the ability, actor kind, credential UUID, argument types and both
  decisions, never user ids or argument values. An exception in the shadowed
  callback is logged as `access.gate_shadow_failed` (exception class only)
  and never changes the decision.
- With `access.use_package_gate` false the legacy callback decides alone,
  exactly as before the package: `GateBefore`'s API-actor rules (no
  super-admin pass for keys, grants and the public door) do not apply until
  the switch flips. The shadow log shows each place where the package would
  decide differently. The legacy callback receives the Gate's arguments
  untouched, named keys included.
- Both switches must be booleans (`true` / `false` in `.env`; `1` / `0` are
  strings and fail at boot), and boot fails when either needs the legacy
  callback and it is not bound.

The §9.4 rule stands: the default flips only after a full minor of shadow
logs with no mismatch other than the ones the design predicts. A failure of
the shadow log itself is swallowed silently (its message could carry
secrets), so an empty log proves nothing on its own: before counting, provoke
one known mismatch in each environment (for example a legacy callback that
answers differently for a test-only ability) and check that it reaches the
channel.
